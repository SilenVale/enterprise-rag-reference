# 阅读笔记

这是对那份企业级制度问答材料的转述，用自己的话记下离线链路、在线检索、生成端、评测门禁，以及 Q1 到 Q14。不把仓库写成某一家机构的生产系统。下面出现的召回率、幻觉率、耗时、篇数、条数，以及「旧版制度误用事故清零」，都是材料里的结果，不是这个仓库测出来的。

## 材料里的结果

只在本笔记里记录，并标明是材料里的结果：

- 检索 Recall@5：材料写纯向量基线 71.2%，三路召回加精排之后 93.4%。
- 幻觉率：材料写从 13.8% 降到 2.1%。
- 制度问答耗时：材料写从 20 分钟降到 30 秒。
- 旧版制度误用：材料写事故清零。
- 文档规模：材料写 18.6 万篇，周增 800 篇以上。
- 评测集规模：材料写 2800 条。

README、演示、简历和评测报告都不写这些。下文若再次写出同一个数，仍是材料里的结果。

## 离线链路

离线要解决三件事：检索用的粒度和生成用的粒度不是一回事；制度文件的版面很脏；制度会修订，不能每次把库推倒重建。

### 父子分块

小块的向量集中，容易找准，可是交给生成模型时前因后果不够。大块的上下文完整，可是一个向量承担的意思太多，检索会漂。材料把这两件事拆开。

文档先按章节或条款切成父块，长度在 512 到 1024 token。父块再切成子块，长度在 128 到 256 token。只有子块做嵌入、进向量索引。命中子块之后，按父块编号把整段父块交给生成。子块负责找准，父块负责把完整条款交出去。父块不再做一次嵌入，避免过泛的向量把索引弄脏。

子块在嵌入之前拼上标题路径，让向量带着「哪一份制度、哪一章、哪一条」的层级。表格不按普通段落切。按行切，每一行都带上表头，这样单独命中一行仍然知道这一格是什么字段。

子块的 metadata 带 `parent_id`、文档编号、版本号。材料在追问里还把内容哈希算进增量比对。父块原文单独存放，命中后按编号取回，向量库不再为了取原文做第二次查询。父块若超过设计上限，先降成「条款加条项说明」；仍然放不下，就注入父块摘要，并带上命中的子块全文。

### 解析与两道闸门

制度文件常见三种脏法：双栏被抽成左右串行、表格断在两页、扫描件和盖章没有可用文本层。

版面分析先认出标题、正文、表格、图示和它们的坐标，再按栏内自上而下、栏间先左后右排成阅读顺序。具体用哪一个版面模型，材料没有写死。

跨页表格的判据是：这一页表尾没有结束边框，下一页第一行又没有表头。两者同时出现，就当成同一张表，合并之后把表头补回去。

没有文本层，或者文本层占比过低的页，走 OCR。盖章挡住的区域要单独处理。OCR 出来的文本同样过质量闸门。OCR 引擎材料没有写死。

闸门有两道。一道是字符保有率：解析结果的字符数，除以原文件里能抽出的字符数。材料举的例子是低于 95% 就判失败。95% 是示例，不是写死的线。双栏若吞掉半栏，会在这一道上失败。另一道是表格还原：比行列数，并抽查单元格，用来拦住表头重复这类合并错误。

失败不能悄悄丢掉。丢掉之后，检索侧不知道库里少了什么，使用人只会以为没有这条制度。处理顺序是先重试：换解析参数，或者改走 OCR。多次仍然失败，进入人工队列。进了人工队列的文件不进索引。材料把底线放在完整，接受慢。

### 增量、去重、废止

材料用周增和总篇数说明全量重建不合适：每次都要重新解析、重新嵌入，费用和时间都撑不住，重建过程中新旧还会混在一起。那两个规模是材料里的结果，见上文。

三件事一起做。

第一，内容寻址。对规范化文本算 SHA-256。同一份制度会在多个系统里以转发、归档、附件等形态出现，材料数了七个系统。哈希相同就不重复入库，也不重复嵌入。

第二，按块做差量。新版本重新分块后逐块比哈希。没变的块复用已有向量。变了的块重新嵌入。消失的块标记删除。材料认为改一条制度时，多数块可以沿用，所以成本卡在「变了的那几块」上。

第三，废止留档。旧制度不能物理删掉，审计要能回答当时看到的是哪一版。旧版打废止标，并带生效日期区间。检索默认滤掉废止和尚未生效的块。审计查询可以显式把废止版本带出来。

新版本先全部写完，校验通过后再做原子切换。切换完成之前，查询仍读旧版。切换失败，把查询指回旧版。禁止先删后插：删除到新数据可见之间会有空窗，中途失败还会留下残缺库。变更靠事件走增量，另外定时按哈希对账，防止事件丢失之后库悄悄漂移。

## 在线检索

在线检索要补上口语和制度文体之间的差距，再把「像什么」「词面上是什么」「这个人能不能看」分成三路，融合之后再精排，最后按分数决定答、提示，还是拒答。

### 查询改写

员工的问法往往比制度条文短、也更口语。材料举的对照是：员工问出差坐高铁能不能坐一等座，条文写的是因公出差乘坐高铁时可报销的座席。向量对这种语体差对齐有限，BM25 更依赖字面，两边都可能找不到。

改写用在线的小模型，不占用生成用的主模型。两级都做。多轮里的指代要带上对话历史，改写成可以单独拿去检索的问题。材料举的例子是把「那一条呢」补成某一份制度的某一条。复合问题拆成 2 到 3 个独立子查询，各自检索再合并，避免一个查询里塞进好几个意图，每个意图的召回都被稀释。

改写是增益，不是前置依赖。原查询和改写查询都参与召回。改写错了，原查询的召回还在，结果不会比完全不改写更差。只有指代或省略很明确时才改写，话题已经换了就不要硬消解。

### 三路召回

材料的三路表从第 3 页断到第 4 页。断开的那一行是「BM25 稀疏」，引擎是 Elasticsearch。下一行是元数据过滤。三路就是向量、BM25、元数据过滤。

- 向量一路用 Milvus 和 BGE-M3。强项是同义改写、口语和跨文体。弱项是条款编号、金额、专有缩写这类要精确对上的词。
- BM25 稀疏一路用 Elasticsearch。强项是条款号、编号和专名的精确命中，而且不需要先有样本。弱项是同义改写对不上。中文分词用 IK。条款编号另留原始 token，做精确匹配，避免被分词拆碎。
- 元数据过滤这一路在检索引擎内部做。硬约束是权限、生效状态、文档类型。它不负责语义匹配。

三路并发，各取 top 50。延迟按最慢的一路算。融合之后精排只做一次。

权限和生效状态必须先过滤。后过滤的做法是先取出向量 top K，再按权限丢掉看不见的。可见文档占比低的时候，候选里大部分会被丢掉，真正能用的召回变少；把 K 放大又会把延迟和成本带高。先过滤是把这些标量条件下推进引擎，在过滤后的子集上检索。Milvus 用 bitset 做预过滤，Elasticsearch 用 filter context：不参与相关性打分，还可以缓存。后过滤不能当成通过路径。无权限的角色提问时，受限制度不出现在候选里。

### RRF

三路的分数不能直接加权。向量分是余弦，BM25 分是另一套量纲，数值放在一起没有可比性。加权之前要做归一化，而归一化用的最小最大会跟着查询分布漂。

RRF 只看每一路的名次。某个候选的融合分，是它在各路里 `1/(k+rank)` 的和。材料写 k 常取 60，本仓库把 k 定成 60。这样不用归一化，也不用给每一路调权重。代价是看不出「第一名比第二名高出多少」。融合这一步只负责候选尽量少漏，排序质量交给后面的精排。某一路明显更可信时，材料认为仍保持 RRF 不加路权，把可信度留给精排，避免又走回调权。

### 精排和三档

召回用的是 bi-encoder：问题和文档各自编码，文档向量可以离线算好，在线只编码一次问题再做近似检索。它快，但两段文本没有 token 级别的交互。精排用 cross-encoder：问题和文档拼在一起过同一个模型，交互更细，每个候选都要跑一次前向，所以不能对全库做。材料用它文首的文档规模说明全库精排不成立，该规模是材料里的结果。

漏斗的最后一层才是精排。模型用材料点名的 bge-reranker-v2-m3。对 RRF 之后的 top 50 到 top 100 排出 top 5。这个区间里具体取多少，材料给了范围，精确取值若自定，要标注「文档未写死」。这个模型加载失败就停住，不换一个别的模型还当作通过。它的 layerwise 特性可以在低层提前退出，用来省算力；换更小的精排模型会动到分流阈值是否还有效，要整层回归。

精排分三档，分数线在评测集上标定，不是先拍一个数，标注「文档未写死」。

- 高分：证据够，正常生成答案，并带引用。
- 中分：有证据但不充分。仍然回答，并明确写上信息可能不完整、建议人工核实。
- 低分：拒答并转人工。拒答日志再用来补知识。

材料把阈值的定法写成：在评测集上看拒答率和准确率怎样一起变化，用业务能接受的答错率反推阈值；上线后按 badcase 和拒答日志再调。

## 生成端

生成要让每一句都能对回条款和版本，并且不把「请不要编造」只写在提示词里。

### 编号引用

命中的父块以 `[1]`、`[2]`、`[3]` 注入提示词，要求每个事实句末尾标上来源编号。展示时编号可以点回原文块，核对数字出自哪一条、哪一版。材料认为合规审计要的不只是答案说了什么，还要答案依据的是哪份文件的哪个版本。编号引用是软约束，模型仍可能不照做。

提示词分成两段。系统说明、格式约束、引用规则放进稳定前缀。检索到的块和用户问题放进变化段。这样前缀可以跨请求复用。

### 出口三道校验

提示词是概率性的。材料的路线是：能用代码拦住的，就不靠提示词自觉。三道都在出口用代码做，不交给生成模型自己判断。

1. 数字。答案里的每个数字，都要能在它所引用的那一块原文里找到。对不上，拦截该句或该答案。金额、日期、比例都抽出来做匹配。这是用来拦住「条文里的补贴被说成另一个数」这类错误。
2. 版本。引用块带版本和生效日期区间。若命中的是废止版本，拦截该句或该答案。全景图的格子写成直接拒答，正文的验收是拦截该句或该答案。按正文做。检索层已经先滤过一次，出口再留一道，防止漏滤。
3. 蕴含。每个句子和它的引用块做蕴含判定，结果分支持、中立、矛盾。材料没有写死用哪一个蕴含模型。字符串完全相同不能当作蕴含通过。不支持的句子先删。删完如果答案还读得通，就只删这一句。删完读不通，整条降级或拒答，不把挖空的句子留在答案里。阈值在评测集上标定。误删的样本进入 badcase，下次回归要能看见。

纵深是三层再加上运营。检索层先过滤权限和生效状态，这是第一道。生成层的编号引用是第二道，偏软。出口的数字、版本、蕴含是第三道，偏硬。拒答日志和 badcase 再送去补知识，让「库里没有」这一类拒答随着补录下降。

### 生成服务

材料写的生产规格是用 vLLM 私有化部署 Qwen2.5-72B。理由有两条：数据不出域；PagedAttention 把 KV cache 分页管理，并发吞吐高于不做分页的推理。72B 这个规格，材料说是在中文制度理解和指令遵循上够用，并且单机多卡放得下；材料还写它和 32B 比过，小一档在条款引用和拒答判断上更常出错。这是材料里的选型说明，不是本仓库已经加载 72B 的记录。

prefix caching 对这套提示词特别合适，因为系统说明、格式和引用规则每次都一样，多轮历史里也有重复前缀。材料要求报自己的首 token 延迟和吞吐，正文没有给出可以引用的实测数字。本仓库在自己测到之前，不把这些延迟和吞吐写进 README。

生成适配留两个档，走同一套引用格式和同一套出口校验。一档是本机跑得动的，给演示和验收。另一档是 vLLM，配置里保留材料所写的 Qwen2.5-72B。验收不要求本机把 72B 加载起来。

## 评测门禁

评测要把「感觉变好了」收成可以回归的指标，并且在指标退步时挡住发布。

### 评测集

材料写的评测集是 2800 条，这是材料里的结果。三个来源：贴近真实提问分布的采样，按问题类型、角色和文档域分层；故意构造的边界，至少包括新旧版本、废止制度、跨条款、权限、表格里的数字；已经修好的 badcase，固化之后防止同一个坑再出现。评测集要版本化，不能把正在用来调参的例子混进去把指标抬高。

本仓库的评测集按本地能跑完来建，三类都要有条目，不把材料的条数抄成自己的条数。

### 两套指标都算

两套都算出来，不并成一套名字。

材料正文那一套：

- 检索：Context Recall、Context Precision、Recall@5。归因先看 Context Recall，该找的文档有没有找到。低了，问题在分块、召回或过滤。
- 生成：Faithfulness、Answer Relevancy。再看 Faithfulness，找到了却答错。低了，问题在提示词、校验或模型。
- 端到端：答案准确率、拒答正确率、引用正确率、耗时。

提示词里那一套：

- 检索：该找的条款有没有进上下文，并报告 Recall@5。
- 生成：答案是否被引用支持。
- 端到端：准确率、拒答正确率、引用正确率、耗时。

拒答正确率单独算。只看成功率时，多拒答会把准确率撑高。评测集里要有「应该拒答」的子集，同时看该拒没拒、不该拒却拒了。

### 门禁看什么

改提示词、topK、分流阈值、RRF 的 k，或更换生成模型，都要跑分层回归。材料写的触发范围还包括检索权重这类参数调整。

门禁卡住的是本仓库自己的三个数：Recall@5、用出口校验失败算出来的幻觉率、端到端准确率。幻觉率按出口没通过的比例来算，不用材料里的 13.8% 和 2.1%。这三个相对本仓库基线退步，超过自定阈值就阻断合并或发布。阈值标注「文档未写死」。

拒答正确率和引用正确率同时报告。它们是护栏，不拿来代替上面三个门禁指标，也不允许靠多拒答把准确率做高。

评测报告只写本仓库这次跑出来的数。

### 裁判

用模型当裁判时，材料指出它会偏向位置靠前的答案、偏向长答案、偏向自己的输出，也会把什么都打成接近的高分。校准做四件事：用一份人工打分的对照看裁判和人是否一致，并定期看有没有漂；裁判不直接给一个总分，而要写出错误点、错误类型和支持依据，方便代码复核；另有一份可执行清单，逐项看数字是否在引用原文里、是否引用了废止版本、每一句是否被引用支持；裁判模型的版本钉死，升级等于换了尺子，历史指标不能直接比较，要重标基线。

没有裁判模型时，门禁以这份可执行清单为准，并在验收里写明。

### 拒答日志

拒答日志分成知识缺失、检索失败、权限不足。知识缺失进入补录队列，补录之后再跑对应的用例。检索失败和权限不足分开记，避免把「不该看」补成「库里没有」。

## Q1 到 Q14

### Q1 为什么用父子分块，块多大

这是粒度问题，不是再找一个折中长度。子块找，父块答，两个目标分开。父块 512 到 1024 token，子块 128 到 256 token，只嵌入子块。标题路径和「表格按行带表头」是配套，不是另一种切法。

材料说块大小要在评测集上对照召回和端到端准确率来选，语义完整优先，不是先拍一个数。映射存在子块 metadata：`parent_id`、文档编号、版本。父块原文独立存放。父块超长就按上一节的两级降级处理，不把父块塞进向量库。

### Q2 脏文档和解析失败

材料把解析当成上线后的第一类事故：检索再准，文本抽错了，答案也会错。处理就是上一节的版面重建、跨页表格、OCR 兜底，加上字符保有率和表格还原两道闸门。字符保有率的 95% 是材料举的例子。

不能静默丢弃。丢了就是知识库上的空洞，使用人查不到，会以为没有这条制度。阈值同样要靠抽样和人工比对来标定，看拦住的里面有多少是真缺陷、有多少是误拦。材料没有把这条线写成唯一的数。

### Q3 索引怎样保持新，为什么不全量重建

材料用 18.6 万篇和周增 800 篇以上说明全量重建的成本和时效都不可接受，重建期间新旧混杂还会造成合规问题。这两个数是材料里的结果。

做法是哈希去重、按块增量、废止打标，再加上版本原子切换。不用主键覆盖来更新：块的边界一变，哈希会大片变化，等于重写；覆盖过程中查询还会读到半新半旧。先删后增有空窗，失败会留下残缺库。调度是变更事件触发增量，定时哈希对账兜底。若要做全量，也要限速，避免打满嵌入服务。

### Q4 为什么在向量之外还要 BM25

单路都有盲区。向量管语义像不像，BM25 管词面准不准，元数据过滤管能不能看。制度问答里条款编号、金额、缩写很常见，正好是向量容易丢的。

材料给出的口径是：纯向量基线 Recall@5 为 71.2%，加上 BM25 后，条款号和编号类查询补了回来，三路再加精排到 93.4%。这是材料里的结果。BM25 可以零样本使用；k1 管词频饱和，b 管长度归一化。它的弱点是同义改写，和向量互补。

中文用 IK，条款编号保留原始 token。三路并发，延迟取最慢一路，各路 top 50，精排只做一次。

### Q5 为什么用 RRF，而不把分数加权

余弦和 BM25 的分数不可比，归一化参数又会随查询漂。RRF 只吃名次，融合分是各路 `1/(k+rank)` 之和，k 取 60。融合层负责少漏，精排负责排准。

材料说 k 在评测集上对 20、60、100 不敏感，所以取常用的 60。给某一路加权重会回到调参，材料选择保持 RRF 不加路权。

### Q6 为什么不用精排模型搜全库

bi-encoder 负责召回，cross-encoder 负责把大约五十到一百个候选排到五个。每个候选都要一次完整前向，全库做一遍不成立。材料用 18.6 万篇这个规模说明这一点，这是材料里的结果。

漏斗是：引擎里的近似检索，然后 RRF，然后 cross-encoder，然后三档分流。模型是 bge-reranker-v2-m3。候选太少会漏掉融合名次靠后的真命中，太多则延迟跟着涨。材料说这个区间是在评测集上对照延迟和指标取的。换更小的精排模型可以换延迟，但分流阈值是否还有效要重新回归。

### Q7 权限为什么要下推进引擎

后过滤会在可见范围很小的时候把 top K 吃空。先过滤把权限、生效状态、文档类型写成标量条件，在可见子集上检索。Milvus 用 bitset，Elasticsearch 用 filter context。

材料说这是对比之后的决定：可见占比低的角色，后过滤的有效召回掉得明显，先过滤能回到不做权限切割时的水平。可见比例很高时，近似最近邻还能用；可见比例极低时，近似检索会退化，可以改暴力扫描或用分区裁剪。材料认为这样延迟仍可接受，没有在正文里给出要抄进本仓库的延迟数字。权限放在文档级，同步进引擎的标量字段，检索时按角色拼过滤表达式。权限变更到引擎可见之间有延迟，口径要单独说明。

### Q8 文档改了，块怎么更新

材料把这题当成数据新鲜度事故：正文已经改版，向量库还是旧块，模型会用过时内容作答。在制度场景里，这就是旧版被误用。

四步。第一，块上带源文档、版本和内容哈希，重切之后分成不变、变化、消失。第二，不变的复用向量，变化的重嵌，消失的标记删除。第三，新版本先全部写入，查询侧仍按版本读旧版。第四，校验通过后原子切换；旧版在校验通过前不删。禁止边查边删。

回滚就是把查询版本指回切换前的那一版，因为旧版还在。事件可能丢，定时用全量哈希对账，发现漂移后仍走同一条增量管道。废止标和生效日期区间留在版本之上，审计可以看历史上某一时刻库里有什么。生成出口的版本校验是最后一道：引用到废止版本，拦截该句或该答案。

### Q9 多轮里的指代怎么检索

不改写，检索拿到的是一个不完整的句子，直接失效。复合问题不拆开，每个子意图都会被稀释。改写要带对话历史，用小模型，原查询同时参与召回。延迟上，材料认为小模型这一步可以和召回叠在流水线里，没有给出要抄的毫秒数。话题切换时，提示约束成「只有指代或省略明确才改写」，并保留原查询。

### Q10 幻觉怎么防

提示词约束是概率性的，合规场景不能接受偶尔违反。约束放到出口的代码里：数字必须见于引用原文，废止版本拦截该句或该答案，蕴含不支持就先删句，删完读不通再整条降级或拒答。再往前，检索层已经先滤了权限和生效状态。

材料写幻觉率从 13.8% 到 2.1%，这是材料里的结果，不是本仓库的门禁读数。本仓库的幻觉率要用出口校验失败来算。

材料对残余错误的说法是：单句都能在引用里找到支持，但跨文档拼出来的结论越界。缓解仍是蕴含校验和拒答阈值，并承认不能靠这个归零。数字和版本检查很轻；蕴含按句批量做，用小模型。材料没有给出要写进 README 的延迟数字。

### Q11 拒答怎么设计

制度问题宁可拒答，也不答错。拒答不是结束，而是运营信号。三档把拒答做成连续的：高分答，中分答并声明可能不完整，低分拒答并转人工。阈值在评测集的拒答率–准确率关系上，按可接受的答错率反推。

拒答日志按知识缺失、检索失败、权限不足分类。只有知识缺失去补录。业务上要同时看拒答正确率：该拒的有没有拒。答错的代价高于拒一次。知识库变化会移动分数分布，回归要覆盖阈值，拒答率异常要有告警。

### Q12 为什么是 vLLM 和前缀缓存

私有化是材料给出的合规约束。vLLM 用分页管理 KV cache，提高并发吞吐。这套 RAG 的提示词前缀长、而且稳定，变化的部分主要是检索块和当前问题，所以前缀缓存划算。多轮历史里的前缀同样可以复用。材料让面试时给出自己的实测，正文没有可引用的首 token 数字。

72B 相对 32B 的比较是材料里的选型说明。显存上要给权重和 KV cache 分卡，并留余量避免溢出。流量高低的调节，材料写的是裁剪精排候选、压缩提示词，不动拒答阈值。

### Q13 评测怎样建，怎样避免虚高

先分清是检索没找到，还是找到了却没答对，端到端掉了才不会拿生成侧的改动去凑检索。两套指标都按上一节计算。

材料的 2800 条是材料里的结果，构成是采样、边界和 badcase。防虚高靠评测集版本化，不把调参用过的例子泄漏进评测；同时报告拒答正确率和引用正确率，避免只看成功率。裁判按上一节的四件事校准。门禁在提示词、检索参数或模型变更时自动回归，核心指标退步就阻断。

维护上，badcase 要分诊、固化、再回归。材料还写按季度对照线上分布重新采样，防止评测集和真实提问脱节。更换裁判模型要重新做人工对齐，并重标基线，旧指标不能跨尺子比较。门禁误拦时，材料的做法是核心指标严、辅助指标宽，豁免要留下评审记录。本仓库的阻断阈值仍标注「文档未写死」，不照搬材料没有写出的那个数。

### Q14 如果重做，会改什么

材料把这题当成取舍题：不能说设计都不用动，也不能说推倒重来。它给了三条例示，并写明要换成自己的取舍。下面只记材料的例示，不把它们写成这个仓库已经做的决定。

- 材料说解析闸门应该更早立起来。先把链路跑通，解析缺陷要到 badcase 才暴露，解析管道返工了一轮。
- 材料说评测集应该更早防泄漏。早期有的 badcase 改了检索参数，又留在评测集里，指标偏乐观。
- 材料说表格按行带表头仍盖不住跨行汇总，例如把各档补贴加总。可以加一条表格问答的专用路径，但当时把优先级让给了拒答和审计。

材料提醒：追问「为什么现在不做」时，每一条都要说清代价和优先级。本仓库不在这篇笔记里另写一套对照答案。
